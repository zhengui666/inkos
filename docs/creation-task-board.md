# Creation task board

The Studio home page accepts two creative inputs: long/short fiction and a brief. A browser-generated UUID is retained through a lost response; identical requests converge on one SQLite task. Existing library books are not migrated, resumed or rewritten by this entry point.

## Planning and execution

The first displayed title/language/length is a clearly provisional project default. Before any foundation is generated, a typed semantic intake worker using the existing architect model/context interprets the full brief, including negations, corrections, explicit language, length and number of sections. Its title, genre, language, finite ending boundary, chapter length and intended resolution are persisted before foundation creation. Host regexes do not decide the production plan. Explicit plan edits override inferred fields. No new model, reasoning-effort or service-tier defaults are introduced.

Short fiction defaults provisionally to one self-contained story, but semantic planning and later plan edits can use multiple chapters/sections. Long fiction has a finite planned ending; neither mode silently extends itself. Publication and completion are separate from chapter count. The ending requires a positive `story-closure` quality observation supported by a retained excerpt from that chapter, followed by verified publication receipts for every chapter. An explicitly requested open ending can be valid; missing story delivery cannot. A completed task records this local acceptance boundary. It does not set a platform's book-completed flag or establish a publishing contract, eligibility or income.

Creation tasks enter the existing scheduler's bounded per-work pool. A slow foundation occupies its own slot while other works can write/review/publish. The existing Goal, work locks, canonical-state checks, immutable revisions, review/revision flow, publication journal and readback adapters remain in use. A foundation committed just before a crash is adopted only when its required prose, structured rules and canonical state artifacts match registered snapshots. Changed or unregistered files are preserved and blocked for reconciliation.

Tasks persist through process restarts. Studio automatically resumes previously runnable creation tasks with a creation-only scheduler; it does not start pre-existing active or paused library books. An explicitly started general daemon can also consume creation tasks. Only one scheduler owns a project. The host still needs continuous service supervision; a stopped/sleeping machine cannot execute background work.

## Pause, plan edits and failures

Pause is durable and checked before new stages/submissions; the active operation receives cancellation and settles without losing its receipt. A submission already in flight cannot be undone by pause. Repeated resume does not create a new work or erase history.

Foundation attempts remain cumulative for audit and backoff. A separate durable failure count charges only settled nontransient failures, so a settled pause or a pause after planning does not spend the later three-failure allowance. Resume does not change either counter. Older records without the new count conservatively retain their known attempt allowance; unknown historical interruptions are not refunded. Existing completed-foundation snapshot checks and uncertain-output reconciliation remain in force.

Pause before editing. Once planning starts, title, genre, language and platform are fixed for that foundation; future chapter length and the ending remain editable after the retained chapter settles. A newly shortened ending must be a future chapter so it can receive a real closure review. Published prose is never rewritten just to fit a new end count.

Creation runs have no application wall-clock deadline or visible-output token cap. User cancellation, native model limits, transport request safety, finite story targets and independent quality/reconciliation safeguards remain. Existing non-creation calls retain their settings.

Known transient model/transport failures back off without resetting durable progress. Unavailable creation review calls remain counted, but do not consume the editorial quality budget. A failed transient writing attempt releases its work slot and persists backoff. At the next due tick the same Goal receives exactly one further attempt, preserving operation keys, cumulative attempt counts, baselines and receipts. The existing adapter must again prove absence before writing. Retry now only advances that due time; it does not reset progress or quality budgets. Unknown outcomes never grant a retry. Repeated quality defects, source/state conflicts, premise-level changes and unconfirmed publication remain blocked; no button silently resets those safeguards.

## Publishing setup and limits

Only configured, existing automatic provider adapters can publish. Set `daemon.publisherConfig` in `inkos.json` (or use the existing `inkos up --publish-config PATH`) to the existing versioned per-work binding configuration. Each new task exposes its generated Work ID. It requires its own verified account/remote-book target binding; an existing book's destination is never copied. The built-in automatic provider is still MegaNovel. Other platform names are not proof of automatic integration.

The board discloses these limits before submission, even when a configuration path has been supplied. The API's `configured` flag and `configurationStatus: "path_provided"` only mean that a path is present. They do not establish that the file is valid, an account is authenticated, a destination is ready, or the platform permits the action. Reading the board does not open a publishing transport or probe an account. `automaticChapterProviders` is derived from the installed default registry; `remoteBookCreation: false`, `emptyBookFirstChapter: false`, and `requiresExistingRemoteBook: true` describe its current built-in capabilities. Platform authorization, content eligibility and real publication require separate verification; a user's account or signed-in session is not proof of platform authorization. Missing adapter capabilities are implementation gaps, not merely account setup.

A missing platform is a clear setup blocker. A missing publisher or missing new-work binding allows local drafting/review and then blocks publication with the retained draft. A configured but wrong/unavailable account or book stops before new writing. Binding setup followed by Resume reloads a Studio-owned creation runner safely; a separately owned general daemon must reload its own configuration. Credentials, CAPTCHAs, identity/tax forms and contracts retain their existing required confirmation/handoff behavior.

Remote **new-book creation and empty-book first-chapter bootstrap are not implemented**. A verified existing editor or previously observed chapter is still required by the native MegaNovel binding. This is a remaining end-to-end delivery gap, not a claim that a two-field brief can already launch a fresh remote series without setup. A missing publication capability stops the task with its reviewed draft retained; it does not finish the rest of a long manuscript while only upload waits. `submitted`, `pending`, exports and user-reported receipts do not count as published. Existing adapters reconcile ambiguous submissions; they never blindly upload again.

## Validation

Core and Studio tests use real temporary SQLite/filesystem state and simulated model/publishing ports. They never create or publish a real book. `scripts/verify-creation-board-ui.mjs` is a browser-only fixture test for two-input entry, repeated clicks, refresh, pause/edit/resume and responsive rendering. Its Chromium launch was blocked by the current execution environment's Unix-socket restriction, including one formal escalation attempt; browser visual/interaction acceptance remains pending and is not represented as a pass.
